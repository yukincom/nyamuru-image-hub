# ネームの表情辞書・外見の英語読み取りと画像寸法の合同確認計画

2026-11-02。顔切り抜きの辞書照合、設定画の外見読み取りと保存まで実装。リサイズとの合同確認は実機試験待ち。新規取込時に、ネームの一場面の表情と設定画の安定した外見を、それぞれ最初の読み取りから英語で記録する。人物3枚参照に渡る英文は、生成前の編集欄で確認できるようにする。

## 採用した辞書と添付プロンプトの扱い

手元の正本は `Desktop/tools/資料/qwen-vl-expression-reference-2026-10-30/catalog.json`。10カテゴリ・86項目、SHA-256は `6bd93e067410380469bdbad8ef13615a9a52439b44d5e4394823f1c5d43b01b6`。指定された `revision-backups/star-eyes-v2` の revision 欄はS070修正までで、正本にはS071の瞳孔修正も記録されている。資料の編集元・見本は元の場所に置き、必要な機械可読データを版・出典とともにアプリへ同梱した。

表情部分は利用者の添付英文を基にした。読み取りプロンプトには次の方針を適用する。

- **部分一致を採用する。** ベース感情・眉・目・口・漫符の5枠とし、目と眉は独立に選ぶ。ベースはC01〜C07のうち役割が `whole_expression` の項目から最大1件。汗などの `feature` を顔全体の感情にしない。見えない・区別できない部位は未判定、漫符がなければ空配列、顔がなければ `faces: []` とする。感情が決まらなくても読めた口や汗は採用できる。
- **省略は証拠にしない。** 黒い塗りやハイライトの省略だけでS053・S054・S066を選ばない。驚いた雰囲気だけでも選ばない。S066には両目が空の円記号として描かれた積極的な根拠が要る。通常の虹彩線が残れば通常目、そこまで読めなければ未判定とする。涙と汗は起点と位置、記号目は線の角・曲率・本数を見る。
- **目全体と虹彩内の模様を分ける。** S070は虹彩内のハート、S071は丸い虹彩の中の星形の瞳孔、S072は虹彩内の複数の輝き。いずれも通常の目の輪郭を保つ。S073の三白眼、S083/S084の片目閉じも、C08の記号置換と区別する。記号目フラグはカテゴリだけでは決めない。
- **IDは出典、生成には部位の英文を使う。** `visual_description_en` は多くが顔全体の一文で、部位別の英文配列ではない。対象に見える部位だけを短い英語句として選ぶ。辞書にその部位の英文がない場合は、画像からの英語の観察と辞書由来の句を区別する。S050を口に使っても、ベースに `expressionless` を足さない。`selected_tags` を一括で生成文に連結しない。
- **設定画にない目を描かせない。** 通常目テンプレートの「二重まぶた・濃いまつ毛・精密な瞳」は外し、目の描き方はimage2に委ねる。image1が構図・ポーズ、image2が外見・ペンタッチ、image3が表情を担当する。英文例は “Use the expression from <image3>: slightly lowered inner brows, half-lidded eyes, and a short, straight, closed mouth.” この例のIDや形は他の顔の既定値にしない。画像の役割を示すラベルは実装では既存の生成テンプレートだけが付ける。

## 顔の切り抜きとQwen-VLの照合

[表情専用プロンプト](../scripts/qwen_face_expression_prompt.txt) が、実際にQwen-VLへ渡す英文の正本。利用者が渡した英文の部位別照合、見るべきポイント、出力形式をここに置く。[同梱辞書](../scripts/expression_catalog.json)の86項目を英語で一度添える。この呼び出しの対象画像は切り抜いた顔1枚で、人物名、候補一覧、全身画像、台詞は渡さない。

1. 原稿の人物領域に一意に対応する検出済みの顔があれば、人物と顔をそれぞれ原寸の原稿から切り抜く。検出領域そのものが顔なら、その1枚を使う。編集用60%画像とは別に扱う。
2. 体だけ検出されて顔の位置が決まらない場合、既存の姿勢読み取りでQwen-VLに対象人物の顔の位置を尋ねる。位置を特定できれば、その範囲を元の人物画像から切り抜く。複数の顔の所属が決まらなければ要確認にする。
3. Qwen-VLが顔画像を見て、ベース感情・眉・目・口・漫符をそれぞれ辞書に照合する。部位ごとに英語の形状句（`extract_en`）と観察根拠（`reason`）を返し、自ら生成用の一文（`qwen_image21_prompt_en`）を書く。役割ラベルは生成テンプレートが持つため、この一文には入れない。通常目にまつ毛や二重まぶたを足す指示も入れない。
4. ニャムルは照合結果を同じ人物領域に記録し、Qwenの表情文を既存の編集可能な演技欄に反映する。顔の向きだけで表情が読めたことにはしない。部位と出典は作品内の `analogImport.expressionReading` に保存し、3枚参照には現在の演技欄を使う。

たとえばQwenが目をS010、口をS050に対応づけた場合、`extract_en` に半目と閉じた直線口の描写、`reason` にその絵でそう読める理由が入る。口のIDだけで顔全体に「無表情」という感情を足さない。これは応答の読み方を示す例で、実画像での判定結果ではない。

設定画の[外見読み取り](../scripts/local_character_reference_worker.py)は、アナログネームのコマ読み取り（RT-DETR領域検出・顔切り抜き・表情辞書照合）とは完全に別パイプラインとし、後方互換の領域分割やRT-DETR/Baberu OCR前処理を残さず、一枚のイラスト（三面図・多角度設定画）から全体を見て恒常的なデザイン特徴を英語句で直接抽出する。被写体が人間（Humanoid）か人外・マスコット・異形（Non-human / Creature / Mascot / Abstract）かを自動判別し、人間の場合は性別・年齢感（`girl` / `boy` / `woman` / `man` / `young` / `elderly` / `child` 等）も削除せず保持して髪型・顔立ち・体型シルエット・服装（レイヤー構造・白黒コントラスト）・装飾品を抽出する。人外・異形の場合は、目の配置・放射状まつ毛・左右非対称の瞳孔や視線・眉/鼻/口の欠如を `face` に、頭と胴の境界・手足や関節の有無・裾の広がり・複数図で示される伸縮/屈曲/ループ等の変形特性を `silhouette` に抽出し、髪や服が存在しない場合は `hair`・`outfit` を空配列に保つ。人物照合に送る候補はIDと採用済みの外見特徴に限る。手入力は原文を保つ。

局所確認はPython 45件、Node 13件が成功し、変更したTypeScript 5ファイルの型診断は0件。模擬Qwenに届く顔の画素と原稿を照合し、顔照合だけに英語の辞書86行が入ること、モデルが書いた文が演技欄に一度だけ入ることを確認した。顔の回答が空または形式不正なら要確認として姿勢と人物照合を保持する。これらは実画像の表情判定精度とは別に確認した結果である。

## リサイズと同時に行う受入確認（後日）

設定画を上限内で登録して既存の外見読み取りを実行し、その人物を含む同じネームを新規取込する。解析に使った画像・保存した画像・生成へ渡す画像を人物領域IDと設定画IDで追う。寸法と英文を別々に判定する。ComfyUI単独実行と比較する際は、実送信寸法、ワークフロー版、seed、指示文を揃える。

| 確認対象 | 合格条件 |
|---|---|
| ネーム取込 | 人物照合・表情読み取りは保存前の原寸切り抜きから行い、VLM内部の整形寸法は別に記録する。例えば1000×500pxの元絵なら保存・image3は600×300px。開き直しても二重縮小しない。 |
| 3Dと設定画 | image1は確定プレビューの縦横各20%。image2は新規登録時に長辺351・短辺248px以内を要求する。以前の4096×2186pxは登録で拒否し、同じ比率の351×187pxを選び直して実送信寸法まで確認する。既存作品を開き直しただけで登録済み画像が縮むとは扱わない。 |
| ラフ表情の実読取 | 黒目塗りの省略、明示的な白丸目、星形瞳孔、半目＋直線口、涙と汗、隠れた口、顔なしを確認する。半目＋直線口でS010とS050が部位単位で共存し、全体感情の二重指定や口角の補作がないこと。曖昧なら該当部位だけ保留する。 |
| 外見の実読取 | 設定画で見える固有の形が最初から英語でobservedに入り、名前からの推測・一時的な表情・辞書見本の外見が入らないこと。日本語注記由来の特徴も確認する。 |
| 通常画面・送信 | 同一人物の同一コマで、編集可能な演技、台帳の外見、正のプロンプト、実際に送った指示を照合する。英語の表情は1回、image1/2/3の順序と手動編集を保持する。5候補の完走・画質は最後の実生成で独立に判定する。 |

上の合同確認では、同じ人物の顔切り抜きと演技欄を見比べ、目・眉・口が原画の可視形状に合っているかを見る。実画像での精度と生成結果は利用者の実機確認で判定し、その後に全体テストを行う。
