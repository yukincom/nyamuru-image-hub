# ComfyUIワークフロー接続の実装計画

作成日: 2026-10-30

**状態: 第1〜5段階を正本へ反映し、局所試験済み。第6段階の実生成受入は未実施。venv・通常サーバー設定は変更していない。** [接続仕様](COMFYUI_WORKFLOW_SPEC.md)を実装の基準とし、[人物のクロマキー透過仕様](2026-10-30-chroma-key-generation-spec.md)を後処理として接続する。

目的は、ComfyUIで作ったワークフローを環境設定から登録・選択し、ニャムルの既存生成操作で使えるようにすること。Desktopの内部Pythonをニャムルから直接起動する方式には移植しない。

## 実装と確認結果（2026-10-30）

- 登録保存、版競合、API形式・入出力対応の検査、設定UI、端末の選択IDを接続。登録のID・版・グラフ・入力・接続先を準備時に固定する。
- 標準APIへ参照を順番どおり送り、5シードを順次実行。各候補の送信前IDと受付IDを保存し、応答喪失・worker終了時も再送せず照合する。途中失敗・未確定では取得済み候補を残し、完了とは表示しない。
- Dialog・会話・音声の既存入口とHermes CLIは選択定義を同じserviceへ渡す。LANの登録・取消し・採用ルートも追加。別PCでの実LAN操作は未確認。
- Qwen人物は選択した緑・青・マゼンタをジョブに保存し、採用1枚だけ色抜き・despillする。固定寸法の出力は縦横比を保って既存の追加処理へ渡す。汎用定義の指示は日本語も原文を保持する。

稼働中のComfyUI 0.43.2に `GET /system_stats`、`GET /object_info`、解放拡張capabilityの読取だけを実施。0・1・3・10参照の配布例は必要ノード・モデル選択肢・入力型の不一致なし。解放確認拡張は未配置だった。推論・画像アップロード・キュー操作・モデル解放は実行していない。

## 2. 実装順序

### 第1段階 入出力契約とQwenの基準ワークフロー

ComfyUIで編集・保存できるQwen Image 2.1 TurboのAPIグラフを基準例として用意する。既存の指示文、参照順、シード、出力寸法、人物・文字・ページ等の用途を照合し、登録データと対応付けの最小形式を決める。

- 新規／画像参照、参照枚数、必要な画像入力と完成出力を明示する。0枚・1枚・複数枚・現行上限の10枚をどの定義で受けるか決め、資料を黙って減らさない。
- 固定グラフで不足する入力を動的に捏造しない。可変入力に対応する標準ノードの形式を確認し、必要ならComfyUIで作った入力条件別の定義を登録する。
- モデル・サンプラー・ステップ数等はグラフの値を保持する。ニャムルが差し込む入力だけを契約として列挙する。
- Qwen用と汎用の指示文処理を明示して保存する。画像生成経路の移行を理由に、承認済み本文・翻訳方針・文字のLLM不要経路を変えない。

この段階の完了は、API形式と入出力の対応を確認した時点。モデルを動かさない照合を生成成功とは扱わない。

### 第2段階 登録保存と環境設定

bridge側に登録定義の一覧・追加・更新・解除と利用可否確認を設ける。新規ファイル候補は `scripts/comfy_workflows.py` と `src/lib/comfyWorkflows.ts`。型・登録保存・対応付けの検証を所有させ、別の推論サービスは作らない。

既存の `LocalImageModelSettings` に、接続先、登録一覧、ファイルから追加・更新、使用する定義、入出力の設定をまとめる。既存の設定更新関数へ統合し、`local: { imageModel }`による全置換や正規化で選択IDが消える経路を解消する。

登録の本体はbridge、選択IDは端末、実行時の固定コピーはjobが所有する。ファイル選択の取消し、更新の競合、保存失敗で現在の選択と登録を壊さない。ComfyUIの通常編集JSONにはAPI形式での書き出しを案内する。

完了条件は、追加→対応付け→選択→再表示→ファイル更新が通常版とLAN版で同じ保存経路を通ること。設定変更だけで生成・作品変更が起きないことを局所確認し、利用者が画面を確認できる段階にする。

### 第3段階 標準APIと既存ジョブの接続

通信の新規ファイル候補を `scripts/comfy_client.py` とし、接続確認、画像送信、実行受付、状態照合、結果取得をまとめる。既存の`nyamuru_comfy_draft.py`にある固定ラフ専用の変換・制約を、そのまま汎用生成へ持ち込まない。

- 登録IDから定義を解決して準備時に固定する。任意のローカルPythonパスやlab rootを実行指定として受け取らない。
- 5候補の各`prompt_id`、シード、取得出力を既存jobに記録する。グラフとアップロード画像は候補間で共用し、1枚ずつ順次送信する。
- 受付前後の切断でも二重実行しないよう、送信前の照合用IDと受付結果を同じjobに保存する。再照合で結果を取得し、自動再送は行わない。
- 取消しは所有するIDだけに限定する。対象指定停止の利用可否を確認し、全体停止に置き換えない。
- 画像取得後は既存候補・選択・履歴へ接続する。ジョブ管理や作品挿入を二重化しない。

完了条件は、模擬ComfyUIとの往復で入力・結果・状態の対応が成立し、現行のlab Pythonを呼ばないこと。実モデルの画質・速度はこの段階では未判定。

### 第4段階 生成入口と常駐ComfyUIの実行管理

生成Dialog・会話・音声・Hermesの入口を、同じ登録定義とジョブ経路へ接続する。ブラウザー内は端末で選んだID・URLを渡し、Hermes CLIは要求で登録IDを必須指定する。CLIのURL省略時はbridgeの明示された既定値を使い、解決済み接続先を準備結果へ返す。CLIがlocalStorageや別端末の選択を推測して読む経路は作らない。環境設定で選んだURLが確認専用に残らないよう、prepareから結果照合まで同じ接続先を使う。LANの許可ルートと結果decoderも揃える。

ComfyUIはDesktop側で起動したまま使い、ニャムルの生成終了で終了させない。LLMの復帰条件を「子ComfyUIの終了」から「自身の生成完了と必要なモデル解放」へ改める。他のComfyUIジョブがある場合の復帰待ちを扱い、全体停止やキュー消去で解決しない。

Python側の`shared_llm_process.py`と`image_generation_lock.py`も対象にする。現行の子プロセスへ継承したFDの閉鎖は外部APIジョブの終了証拠にならない。送信後のbridge/worker異常終了でも、guardianが保存済みIDとAPIの状態を照合し、実行中・結果不明ならLLMを復帰しないようにする。

完了条件は、同じ定義を各入口が使い、候補選択で止まり、他のジョブとユーザー起動のDesktopを維持すること。VLM・OCR・音声分類の接続は変えない。

### 第5段階 人物のクロマキー透過を接続

APIによる本画生成と候補取得が通った後、[透過仕様](2026-10-30-chroma-key-generation-spec.md)に従って背景色・最終指示・採用後の色抜き・despillを接続する。

背景色はその人物ジョブの値として保存し、候補5枚を同じ色で作る。採用した1枚だけをコードで透過する。ページ・コマ・背景・文字の扱い、元のあたりの保持、新規レイヤー追加は既存の責務を使う。

完了条件は、合成PNGでの色抜きと採用操作の局所確認。モデルが単色背景を作れるか、実画像の輪郭を保てるかは次段階で判定する。

### 第6段階 実ワークフロー確認と切り替え完了

利用者が指定した参照画像を使い、最終送信プロンプト全文・参照順・寸法・5シード・使用定義を事前提示して実生成を行う。まずQwenの代表例でAPI受付→5候補→1枚採用→透過→新規レイヤー追加まで確認する。必要な用途別確認は下表に従い、未確認の用途を完了扱いにしない。

ComfyUIで変更したグラフを再書き出しし、環境設定から更新した定義が次のジョブへ反映されることも確認する。標準APIと入力対応で使える別グラフを使い、Qwenの固定ノード番号だけに依存していないことを確かめる。

利用者の画面確認後に必要な全件テスト・ビルドを実行する。検証用に起動したサーバーだけを止め、プロセス終了とポート解放を確認する。作業前から動くDesktop・ニャムルを一括停止しない。

旧lab参照はコード・起動設定・Hermes入口・必要な試験から解消した範囲を記録する。旧venvや環境フォルダーの物理削除は別の明示指示で扱い、この計画の完了条件には含めない。

## 4. 第1段階で確かめる実行上の差

次はAPI方式の採用を取り消す理由ではなく、Qwenの基準ワークフローを決める際の確認点。

- Desktop coreには `TextEncodeQwenImage21`、`QwenImage21Cache`、`ModelAttentionBackend` がある。CPU参照キャッシュとPyTorch attentionは標準ノードで指定できるが、実グラフ・現環境での動作は別に確認する。
- `TextEncodeQwenImage21`はnegative側もencodeする。現在のCFG=1向けpositiveのみの処理との速度・メモリ差を測り、未使用部分の省略が必須かを判断する。
- CPU VAEには正式な起動オプションがある。常駐サーバー全体へ影響するため、採用環境の設定と他のワークフローへの影響を確認する。
- 現行の16GiB MPS上限と工程ごとのプロセス終了は、常駐APIへ自動では引き継がれない。5候補でピークメモリと解放後の状態を確認する。
- 標準ノードで必要条件を満たせない場合だけ、不足を具体化して独立カスタムノードの範囲を決める。Desktop coreへ直接パッチを当てたり、先にvenvをコピーしたりしない。

参照: [ComfyUI標準API](https://docs.comfy.org/development/comfyui-server/comms_routes)、[接続仕様](COMFYUI_WORKFLOW_SPEC.md)。ローカルcoreの確認対象は `comfy_extras/nodes_qwen.py`、`comfy_extras/nodes_model_advanced.py`、`comfy/cli_args.py`。
