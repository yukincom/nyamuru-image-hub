# 使い方

この文書では、Nyamuru 🐱 Image Hubの起動、アナログネームの取り込み、編集、保存までを案内します。

## 文字の種類を変更する

紙面またはレイヤー一覧で文字を選択し、文字ツールの「情報」タブで「種類」を選ぶと、フキダシ・描き文字・写植文字を切り替えられます。OCRの読み取り結果も本文・位置・原字画像を保って変更できます。Tで空き場所をクリックして写植文字を追加する操作も使えます。種類の切り替えはUndo／Redoできます。

## 1. 通常の起動

必要なものはNode.js 22.12.0以上です。

```bash
npm ci
npm run dev
```

ターミナルに表示されたlocalhostのURLをブラウザで開きます。通常のネーム編集、構成YAMLの書き出し、生成プロンプト、コマ編集にはPythonや画像解析モデルは不要です。Mac側の作品フォルダ保存・読込にはローカルbridgeを使います。

作品本文と作業画像は編集中のメモリー内にだけ保持します。ブラウザーへの自動保存・起動時の自動復元は行いません。ヘッダーの「保存」で作品フォルダーへ明示保存してください。再読み込みや終了で未保存の編集は失われます。保存済みの作品は「作品フォルダを開く」で再開できます。端末設定の記憶は作品保存とは別です。

新規作成では、シリーズ作品・読み切りのどちらでも、最初にそのエピソードを置くフォルダを選択または新規作成します。登場人物のデザイン画像、舞台設定のMarkdown／テキスト、紙のネーム画像を選ぶ画面は、このフォルダから開きます。編集開始時に、選んだフォルダの直下へ次の作業用フォルダを作ります。既にあるファイルや利用者独自の元データフォルダは移動・変更しません。

```text
選択したエピソードフォルダ/
├── name_data/        # ネームとNyamuruの編集データ
├── draft_data/       # 生成後の下書き
├── manuscript_data/  # 人間が描き込んだ清書
└── export_data/      # 書き出し用
```

シリーズ作品では、次のエピソードを作る際に前回選んだ親フォルダを最初に表示します。読み切りは選んだフォルダだけで完結し、シリーズ台帳を前提にしません。このフォルダ選択はmacOSのローカル起動版で使用できます。

シリーズ作品では、新規作成時に保存済みシリーズを選ぶか、作品情報へシリーズ名を入力できます。作品フォルダへの「保存」や、人物・舞台設定の保存でシリーズ共通の台帳も更新します。「環境設定 → データ管理」の構成YAML書き出しは、この台帳保存とは別の受け渡し用操作です。同じシリーズから新規作成すると、保存済みの人物と資料が安定IDで追加されます。作品タイトルや話数を直しても、内部IDで同じシリーズ・エピソードを追跡します。

シリーズ人物のデザイン画像は「人物」画面で複数登録できます。画像を登録しただけでは解析されず、「特徴を抽出」を押した1枚だけをローカルVLMへ渡します。操作とデータ形式は [シリーズ人物資料と照合特徴](./SERIES_CHARACTER_CATALOG.md) を参照してください。

macOSでのシリーズ台帳の保存先は `~/Library/Application Support/Nyamuru Manga Name Studio/series-common/<シリーズID>/series.yaml` です。既存の `series.omny.yaml` は互換読み込みでき、明示保存時だけ新しい名前へ保存します。旧ファイルの保持と新旧競合の扱いは[保存の説明](./PROJECT_SAVE.md)を参照してください。

作品の用紙・基本表現色・解像度は、環境設定の「レイアウト」→「印刷・原稿設定」→「変更」で編集し、「設定を適用」で確定します。「キャンセル」では元の値を保ちます。完成画像の寸法表示、画像書き出し、生成指示はこの設定を参照します。印刷所や基本表現色を選ぶと対応する推奨dpiが反映され、詳細設定で任意のdpiも指定できます。

描画中にT・ズームへ持ち替えるだけなら、線と選択を保持したまま表示を切り替えます。環境設定も「手描き・編集」から開き、表示・モデル設定の変更だけでは描画をPNG化しません。文字の実編集、作品のレイアウト・生成ルール・データ管理、ぬりたしの変更、ページ切替、保存・画像書き出しでは描画を確定します。3D背景の編集中は構図も保存するため、持ち替え時に確定します。確定に失敗した場合は描画を残し、切替先の編集へ進みません。

描画対象やマスクに作業用の囲み枠は表示しません。投げ縄は囲んだ範囲を現在のレイヤー画像サイズで切り詰めず保持し、Shiftで追加、Option/Altで差し引きます。選択だけでは作品やUndoを変更せず、意図して指定した選択輪郭とベクターの操作点は表示します。

選択した行と、実際に所属する親フォルダーを緑で表示します。コマ枠の行を選ぶと枠と所属コマが緑になり、枠の操作点が出ます。コマ外の文字や人物を選んでも、無関係なコマは選択表示しません。階層は字下げで示します。

各ページのコマフォルダーは、初期状態ではすべて閉じています。フォルダーはレイヤーパレットの開閉ボタンでだけ開閉します。手で開閉した状態はページを移動しても保ち、編集画面やレイヤーを選択しても、目を切り替えても、レイヤーを追加しても開閉状態を保ちます。文字レイヤーの目では文字を隠す・再表示できます。非表示の文字は画像書き出しと生成時の文字指定にも含めません。

カーソルが編集画面上にあるときは、フォルダーのボタンにフォーカスが残っていてもSpaceを押しながらドラッグすると画面を移動できます。文字入力・プルダウン・メニューの操作中は、その操作でSpaceを使います。

文字は種類を問わず「テキスト1」「テキスト2」…と表示し、レイヤーと文字ツールの情報見出しで同じ名前を使います。情報タブでは種類（フキダシ・描き文字・写植文字）と本文を編集し、フキダシの場合は話者・しっぽ・結合先を設定できます。

文字ツールパレットはTキーまたは文字ツールから開き、×で閉じます。写植文字は、文字ツールでキャンバス上の置きたい位置をクリックして作成します。レイヤーの表示切替・選択・道具の切替では開閉せず、開いているタブとウィンドウ位置を保持します。

追加した通常フォルダーも、左の目で中の表示をまとめて切り替え、右端のロックで中を固定できます。目を隠しても各レイヤーの目の状態は保持します。フォルダー名をドラッグすると中身ごと順番を変更し、レイヤーをフォルダーの中央へ重ねると中の一番上へ入ります。同じフォルダーへの入れ直しや別フォルダーへの移動では、フォルダー自体の順番は変わりません。フォルダーの解除は、選択後に上部の削除操作から行います。通常フォルダーも人物フォルダーも、選択中は行全体を同じグリーンで表示します。

人物などの生成画像は、元のあたりを保持し、同じフォルダーのあたりレイヤー直上へ新規レイヤーとして追加します。あたりや既存レイヤーの表示とロックは保持し、生成画像を隠せば元のあたりを確認できます。

描画やレイヤー移動は、ボタンを離して確定した変更を一回のUndoで戻せます。操作途中のEsc、入力の取消し、ウィンドウのフォーカス喪失では、その未確定操作だけを取り消します。既に確定した線は保持します。レイヤーを動かして開始位置へ戻しただけなら履歴を増やさず、Redoも保持します。

選択範囲の保持と、描画画像の確保には別の制限があります。投げ縄は縦の走査行数が16384行を超える場合や、輪郭が複雑で計算量が大きすぎる場合にエラーとなり、前の選択を保持します。横に長い選択でも計算量が小さければ保持できます。実際の画像領域は各辺16384px・合計1億pxが上限で、ペンは選択内の筆跡に必要な領域、トーン作成は選択全体に必要な領域を確保します。上限を超える描画は切り詰めず拒否し、選択・原稿・Undoを保ちます。範囲を小さくして再試行できます。上限内でも端末の空きメモリーによって扱える量は異なります。

生成の実行先は環境設定の「モデル設定」で選びます。クラウドの選択と、成人指定作品での利用規約確認は別の項目です。ローカルへ切り替えても確認済みの状態は保持します。設定を保存できなかった場合はエラーを表示し、直前に保存できた値を使います。この端末設定の変更で作品データは更新しません。

## 2. アナログネーム取り込みの準備

画像解析には次の外部コンポーネントを使用します。

- [RT-DETRv4-X Manga109-s v2](https://huggingface.co/tori29umai/rtdetrv4-x-manga109s_v2): コマ・文字領域・顔・身体の検出
- [Baberu OCR](https://huggingface.co/genshiai-daichi/baberu-ocr): RT-DETRが検出した文字領域の軽量認識
- [WD ViT Tagger v3](https://huggingface.co/SmilingWolf/wd-vit-tagger-v3): 一人分の人物切り抜きに対する表情だけの補助候補

Python 3.10〜3.13と、初回セットアップ時のインターネット接続が必要です。次のコマンドを実行すると、取得対象、容量、ライセンス、保存先を表示して確認を求めます。

```bash
npm run setup:vision
```

同意後、画像解析専用の仮想環境、検証済みのBaberu OCR・RT-DETR・WDモデルと固定model cardを、Git対象外の `.local-vision/` へ導入します。アプリを起動しただけではダウンロードしません。

導入状態は次のコマンドで確認できます。

```bash
npm run bridge:check
```

保存先の変更やトラブルシューティングは [ローカル画像解析連携](./LOCAL_VISION_BRIDGE.md)、ライセンスと固定バージョンは [ローカル画像解析コンポーネントとライセンス](./LOCAL_VISION_COMPONENTS.md) を参照してください。

## 3. アナログネーム取り込みを使う

アプリを起動します。

```bash
npm run dev
```

アプリの「新規作成」を開くとローカル連携が自動で起動し、作成完了またはキャンセル時に終了します。「紙のネームからコマを読み取る」を選びます。

1. 画像ファイルを選ぶか、macOSではスキャナーを起動します。
2. 各画像を確認し、必要なら90度ずつ回転して正立させます。
3. 原稿に合わせて上下・左右のコマ間隔と枠線幅を指定します。
4. 「解析開始」を押します。
5. 原画と解析結果を見比べ、使うページを確認します。
6. 「編集開始」を押し、通常の編集画面でコマ・人物あたり・フキダシを調整します。認識した文字と輪郭、レベル補正した手書き原本は、同じ吹き出しフォルダー内の別の子として選択できます。原本は初期非表示で、原本の目で再表示できます。表示・非表示は保存され、フォルダー開閉では変わりません。フォルダーを固定すると全体が固定され、中の子だけを解除することはできません。親の固定解除で子も解除され、その後は個別に固定できます。 固定は手動編集の誤操作防止用です。AI・音声・エージェント操作は固定中でも受け付け、操作後も固定を維持します。

画像を選択しただけでは解析されません。「解析開始」を押した時だけローカルbridgeへ送られ、外部サービスには送信されません。

### スキャナーを使う場合

macOS標準のイメージキャプチャを利用します。複数枚を続けてスキャンした後、ピンク色の「取り込みを終了」を押してください。明示的に確定またはキャンセルしたセッションのスキャン元は破棄されます。強制終了時だけ次回起動時に再接続または破棄を選べます。

## 4. コマを調整する

- **内枠スナップ**: コマをA4原稿の内枠へ吸着します。
- **コマスナップ**: 辺や頂点を、作品に設定した上下・左右のコマ間隔へ吸着します。
- **コマシンクロ（実験的）**: 接合している頂点や揃った境界を局所的に連動します。
- **Shift＋ドラッグ**: ドラッグ開始位置を基準に、水平または垂直へ移動します。
- **コマ合体**: Shift＋クリックで複数コマを選び、フキダシを保ったまま1コマへ統合します。

辺をドラッグすると平行移動し、多角形モードでは頂点を個別に編集できます。複雑な斜めコマでコマシンクロが期待どおり動かない場合は、コマシンクロをOFFにし、コマスナップとShift移動で調整してください。詳しい仕様と既知の制限は [このフォークの機能](./FORK_FEATURES.md) にまとめています。

人物とフキダシは紙面上で選択できます。本体のドラッグで移動し、四隅のハンドルで拡大・縮小します。右側のフォームと紙面上の表示は同期します。

話者がコマ内の人物に一意に対応しているフキダシには、ベクターのしっぽが表示されます。フキダシを選択し、話者枠内の黄色い先端をドラッグすると接続位置を調整できます。「しっぽあり」で表示を切り替えられます。モノローグは、人物側ほど小さくなる2〜3個の楕円で接続します。

「形」の「自動」を押すと、ト書き・セリフ・明示された話者／モノローグ・人物の描写範囲・フキダシと人物の位置から、思考・ささやき・震え・フラッシュ・キャプションなどをコードだけで選びます。文章LLMは起動しません。明示的なナレーション、既存の四角／キャプション、時間経過の定型表現を通常会話より優先し、それ以外は保守的に「ふつう」にします。確定後は手動で変更できます。

新規作成で読み込むネームテキストが `ナレーション：本文` または `ナレーション「本文」` の形なら、話者なしの四角フキダシとして取り込みます。元のネーム本文と照合情報は従来どおり保持します。

新しく作る吹き出しのデフォルト線幅は、ネーム画面の `T` サブメニューで指定します。変更しても配置済みの吹き出しは変わりません。個別の線幅は、吹き出しを選択（V）またはダイレクト選択（A）し、ペンの太さパレットをクリックして変更します。ベクター線と同じpx単位で指定し、作品の解像度に応じたmm値を保存します。本体としっぽに適用され、元に戻す・やり直しに対応します。配置済みの吹き出しまたは写植文字を選ぶと、その文字だけの書体を変更できます。新しく追加する文字の基本書体は `環境設定` → `レイアウト` で指定し、変更しても配置済み文字の見た目は変わりません。

`T` の文字設定は、上から「書体・太さ・サイズ・方向」の縦一列です。書体名は折り返さず、長い名前は省略表示し、マウスを重ねると全文を確認できます。

文字サイズは `T` の文字設定で数値入力またはスライダーから変更できます。表示は入力中に更新され、スライダーの一回のドラッグ、矢印キーの押下、数値入力からEnter／別の欄へ移るまでを、それぞれ一回の「元に戻す」で戻せます。サイズ欄内でも⌘／Ctrl+Zとやり直しを使えます。無効な入力は作品へ適用せず、同じ値の再指定では履歴を増やしません。

PC内フォントは起動時に前回の一覧との差分を確認し、変化した場合だけ候補を更新します。手動の再読込は不要です。対応ブラウザでは端末内の書体名だけを読み、フォントファイルを送信する処理はありません。

### 人物ごとのアクションを入力する

アナログ取込由来の人物には「原画から演技を読む」が表示されます。押した時だけ、その人物1人分の保存済み切り抜きをlocalhostのVLMへ渡し、描写範囲、姿勢、前後左右と上下の向き、顔、手足の演技を候補化します。コマ全体や他の人物は渡しません。

描写範囲と姿勢は別項目です。「胸から上＋立っている」「腰から上＋走っている」のような組み合わせを保ち、切れて見えない脚の形は補完しません。等身はVLMで推定せず、登場人物設定の値を使用します。結果は候補として表示され、「候補を反映」を押した時だけ人物欄へ入ります。反映後も描写範囲とアクションを手で修正できます。

この機能にはローカルのQwen3-VL/MLX環境が必要です。`npm run bridge:check-vlm`で配置を確認できます。WDを導入済みの場合は、表情だけの補助候補を同じ一人分の切り抜きから取得します。WDの弱い信号だけで観測事実や感情分類を書き換えず、Qwenが画像から独立に確認した候補と出典を人間が確認します。WDが利用できなければ従来のQwen-only解析を続けます。モデルの自動取得や外部サービスへの送信は行いません。

コマ全体の「ト書き」には場面・カメラ・構図を入力し、各人物欄の「アクション」には、その人物だけの表情・姿勢・視線・動作を入力します。「コマ XXの人物へ注入」を押すと、ローカルLLMが作品情報、舞台設定、人物像、現在と前後のコマ、セリフを読み、表示中のコマのト書きと人物アクションをすり合わせた完成文に置き換えます。画像読み取りの確かな向きや姿勢は残し、重複を整理し、曖昧な解釈をト書きの明示情報で補います。「怪訝」などの具体的な表情の言葉も残すよう指示します。台本は取り込み済みの各コマの情報を使い、原本全文を別途送る処理ではありません。背景・フキダシ形状・ト書き・他のコマは変更せず、反映後も人物欄で自由に修正できます。Qwenの画像生成では、生成指示と参照資料名を英訳する用途にも文章LLMを使います。

生成画面の「生成指示」は直接編集できます。生成完了後も本文を書き換えて、同じ参照資料で次の生成を実行できます。前の生成結果は生成履歴に残ります。実行中は指示を固定します。ここでの修正は今回の生成に使い、作品の作画設定や描き方欄には書き戻しません。

`npm run dev` のローカル起動版は、既定の `auto` モードで8080の起動済みMLXサーバーを自動で共用します。未起動なら、既存の `~/mlx-server/start_server.sh` を非対話で呼び出します。「環境設定 → AIモデル → 文章LLM」に保存した `models.conf` のエイリアスは、この起動時だけ使います。環境やキャッシュ済みモデルがなければエラーを表示し、インストールやダウンロードはしません。画面にはbridge・LLM準備・文章処理の各段階を表示します。

参照テキスト候補はファイル名・見出し・scopeの決定的な順位で選び、上位がほぼ同点なら利用者の選択に戻します。フキダシ形状も上記のコード規則で決めるため、この2用途では文章LLMを起動しません。

Nyamuru Image Hubが今回の文章処理のために起動したLLMは、処理後に終了します。同じモデルを使う明示処理が重なった場合は、最後の処理まで保持します。元から起動していたLLMは文章処理後も動かしたままです。bridgeは処理の間だけ利用権を取得し、他の利用が終わるまで停止しません。新規作成、文字スキャン、参照テキスト候補、フキダシの「自動」だけでは文章LLMを起動しません。

既定の接続先は `http://127.0.0.1:8080/v1/chat/completions` です。接続先を変える場合は、localhost上のURLだけを `NYAMURU_PANEL_ACTION_LLM_URL` で指定できます。自動起動はHTTPの `/v1/chat/completions` に対応し、そのホスト・ポートでMLXを起動します。

```bash
# 自動共用（既定）
npm run dev

# Nyamuru Image Hubが起動するLLMだけを使う単体モード
NYAMURU_PANEL_ACTION_LLM_MODE=managed npm run dev

# 中央で常駐させたMLXを借りる共有モード
NYAMURU_PANEL_ACTION_LLM_MODE=external-shared \
NYAMURU_PANEL_ACTION_LLM_URL=http://127.0.0.1:8080/v1/chat/completions \
npm run dev
```

`external-shared` は起動済みLLMだけを利用し、未起動時の自動起動を行いません。`auto` と `external-shared` は `model=default_model` を送るため、保存したエイリアスで共有サーバーのモデルを切り替えません。`GET /v1/models` は互換APIの応答確認に使います。実際の起動モデルはサーバーの起動設定とログで確認してください。

画像生成は「LLMで英訳 → 英訳を保存 → 文章LLMを停止 → ComfyUIを起動 → 画像生成 → ComfyUI終了 → 元の文章LLMを復帰」の順です。原文と英訳は生成ジョブに別々に保存します。英訳の保存やLLM停止を確認できなければ、ComfyUIは起動しません。元から起動していたLLMは、生成に使ったすべてのComfyUI処理プロセスの終了後に、同じ起動引数・環境変数・作業フォルダで自動復帰します。起動情報は復帰用プロセスのメモリだけに保持し、作品や設定ファイルには保存しません。今回だけ起動したLLMは復帰させません。

共有LLMの自動復帰はmacOS・Linuxで、同じユーザーが起動したプロセスに対応します。画像生成中は他のアプリからもそのLLMを利用できません。生成画面やNyamuru Image Hubを閉じた場合も、送信済み画像の完了を待って復帰します。生成失敗時も復帰処理を行います。画面の完了表示や通信の切断だけでは終了と判断せず、ComfyUI処理プロセスの終了を待ちます。アプリを再起動しても、この処理やLLM復帰が残っている間は別のLLMを起動しません。別のLLMが同じポートで起動した場合は上書き起動しません。

「環境設定 → AIモデル」では、文章LLMと画像VLMを別々にこの端末へ保存できます。文章LLMは `models.conf` に登録済みのエイリアス、画像VLMはローカルcacheにあるHugging FaceモデルIDを指定します。欄の保存だけでモデルを起動したり、作品データを書き換えたりはしません。無効な値、未起動時に指定した未登録LLM、未保存VLMは実行時に拒否し、自動取得しません。

MLX環境の場所は `MLX_SERVER_DIR`、設定ファイルは `MLX_MODELS_CONFIG`、画面設定がない単体モード呼び出しのエイリアスは `NYAMURU_MLX_MODEL_ALIAS` で明示できます。これらは起動ターミナル側の設定で、作品テキストからコマンド・モデル・パスを指定することはできません。設定済みのスクリプトを使うだけで、環境を再構築しません。作品のテキスト情報をlocalhost上のLLMへ渡し、原稿画像は渡しません。単体モードで管理対象外のLLMが接続先にある場合は、その外部プロセスを止めたり切り替えたりせず処理を中止します。

公開ページ・単一HTMLだけではプロセスを起動できません。自動起動が必要な場合は `npm run dev` のローカル起動版を使用してください。

### 選択中のコマから作画用4値ラフを1枚生成する

ComfyUIを `http://127.0.0.1:8188` で起動し、`animagine-xl-3.1.safetensors` をチェックポイントへ配置してから、コマ編集画面の「作画用ラフを生成」を押します。確認画面には、選択中のコマから組み立てたプロンプト、`manga-base`生成プロファイル、モデル、解像度、Steps、CFG、Seedが表示されます。「生成して自動保存」を押した時だけ、固定ワークフローをlocalhostのComfyUIへ送ります。`manga-base`は生成仕様の名前であり、学習済みLoRAを必要としません。

この作画用ラフは512×512px・1枚です。Animagine XL 3.1にはモノクロの未仕上げ線画を生成させ、ローカルbridgeが線と階調を4値へ変換します。黒 `#000000` は線と確定黒ベタ、赤 `#E60012` は濃トーン候補、水色 `#00D7E8` は薄トーン候補、白 `#FFFFFF` は紙と背景を表します。bridgeはPillowでPNGのchunk末尾、decode、全pixelを検証し、browserもdata URLをdecodeして台帳のbyte数とSHA-256に一致した画像だけを表示します。変換結果は確認画面へ表示され、必要なら「4値PNGを保存」からダウンロードできます。ComfyUIとモデルの自動起動・自動ダウンロードは行いません。

初回は確認画面でエピソードフォルダを選択してください。ブラウザには、そのフォルダを直接表すpathではなく、ローカルbridgeが発行したopaque tokenだけを保持します。「生成して自動保存」を押すと、ComfyUIへ送る直前のストーリーOMNY、生成計画、固定workflowを先にsnapshotし、ComfyUIのoriginal PNG、変換後の4値PNG、sanitized provenanceを次へ自動保存します。

```text
選択したエピソードフォルダ/
└── draft_data/nyamuru/
    ├── ledger.sqlite3
    └── artifacts/sha256/...
```

台帳は論理jobと各attemptを分け、`created`、`queued`、`succeeded`、`failed`、`outcome_unknown`を記録します。各status eventには、その時点のsanitized error全文と不変provenance SHA-256をappend-onlyで保存します。ComfyUIの`/prompt`、`/queue`、`/history`は外部実行状態を再照合するための証拠であり、episode台帳そのものの代わりではありません。再実行は同じattemptの上書きではなく、画面の「新しいversionを生成」から新しいattemptとして行います。送信時のtimeoutやbridge切断は結果不明として保存されるため、自動retryせず、「ComfyUIと再照合」を押してください。`/queue`や`/history`のHTTP error、壊れたJSON、上限超過応答も実行失敗の証拠ではないため`outcome_unknown`を維持し、明示的なComfyUI execution errorまたは完了historyの出力欠落だけを`failed`にします。retry元になるのはbridge台帳から取得できたattemptだけです。bridgeを再起動しても、同じopaque tokenから保存済み台帳を読み直せます。

生成成功と、人間の採用判断は別の状態です。成功済みで完全検証された4値PNGに対して「採用候補」または「見送り」を明示するまでreviewは未確認のままで、生成結果をOMNYへ自動反映しません。reviewはrequest nonceと期待revisionを使うappend-only eventで、複数タブの競合時は古い判断を上書きせず再読込を求めます。後工程が4値PNGを読む場合は、browserから画像dataやpathを渡さず、`job ID + attempt ID + manga_base_composite SHA-256 + OMNY/plan/workflow snapshot SHA-256`を必須にし、同じ成功済みattemptに結び付くbundleだけを台帳から再検証して解決します。

表示されるPNGは4領域を1枚に重ねた作業用画像です。領域ごとのレイヤー分解やPSD出力は行いません。

接続先を変える場合は、localhost上のURLだけを `NYAMURU_COMFYUI_URL` で指定できます。

```bash
NYAMURU_COMFYUI_URL=http://127.0.0.1:8188 npm run dev
```

アプリ側のローカルbridge URLとbridgeの`--host`は、HTTPのloopback（`localhost`、`127.0.0.1`、`::1`）だけを受け付けます。LANアドレスや外部URLへ作品データを送る設定は拒否されます。

## 5. 構成データ・作画設定と画像生成

構成データは、作品情報、素材、コマ、人物、フキダシ、台詞などを記録するYAMLです。「環境設定 → データ管理 → 構成データを書き出す」で `作品名.yaml` を保存できます。公開ドキュメントの「生成プロンプト」には、ストーリー原稿をこのデータへ構造化するための指示があります。

作画・演出ルールは「環境設定 → 生成ルール」で編集し、「作画設定（YAML）」で受け渡します。控えの `作品名-settings.yaml` はOFFの候補も保持します。画像生成に渡す `作品名-generation.yaml` は有効なルールと仕上がり仕様を含みます。公開ドキュメントの「生成ワークフロー」の案内に従い、構成データと生成指示を組み合わせます。

- 構成データ: 作品情報・素材・ネーム（内部データモデル: NDM、YAML形式）
- 作画設定・生成指示: 作画・演出・レイアウトのルール（内部仕様: Open Manga Artwork YAML）
- 初期スタイル: [standard-settings.yaml](../src/content/standard-settings.yaml)
- 生成ワークフロー: [agent-manga-generation-workflow.md](../src/content/agent-manga-generation-workflow.md)
- 旧版の使い方案内（保管資料・現行手順ではありません）: [旧版フォルダ](../archive/legacy-howto-2026-09-05/README.md)

## 6. スタンドアロン版

通常のビルドでは、単一HTML版も `dist/standalone/nyamuru-image-hub.html` に生成されます。

```bash
npm run build
```

単一HTMLだけを作る場合は次を使います。

```bash
npm run build:standalone
```

スタンドアロン版では通常の編集、構成YAMLの書き出し、作画設定YAMLの読み込み・書き出しを利用できます。構成YAMLの読込画面はありません。ローカル画像解析にはlocalhostで動くbridgeが必要なため、公開サイトや単一HTMLだけではアナログネーム取り込みを利用できません。

再配布時は、同じフォルダへ生成される `THIRD_PARTY_NOTICES.txt` も一緒に配布してください。
