# 2026-10-07 ComfyUI実行と文章LLMの切り替え

## 修正した問題

Qwenの生成画面は直接ジョブを起動しており、8080の文章LLMを停止する処理を通っていなかった。停止・復帰処理は、使われていないKrea2画面と常駐ComfyUI HTTPサーバーに結び付いていた。

## 実行順序

1. 起動済みの文章LLMを利用する。未起動なら既存設定で今回だけ起動する。
2. 生成指示と参照資料名を英訳し、原文・参照画像・英訳・SHA-256をジョブへ保存する。
3. 英訳保存の確認後、8080のLLMプロセスを終了する。ここではComfyUIを監視・照会しない。
4. 保存済みの英訳を使い、Qwen用ComfyUIランタイムでencode・sample・decodeを実行する。
5. 生成結果を保存し、すべてのComfyUI処理プロセスの終了を待つ。
6. 元から起動していたLLMを、同じ起動引数・環境変数・作業フォルダで復帰する。今回だけ起動したLLMは復帰させない。

このアプリのQwen実行はComfyUIのPythonランタイムを各処理プロセスで使用する。常駐HTTPサーバーを起動する構成ではない。外部で手動起動した別のComfyUIを監視・停止する機能は追加していない。

## 変更内容

- Qwenのprepareは英訳と永続保存だけを行う。submitは保存済みjob ID・入力ハッシュ・停止確認済み利用権を受け取り、生成を起動する。
- 英訳は `generation-prompt.json` とそのSHA-256に保存し、元の `request.json` は変更しない。workerと各ComfyUI処理が読み直して検証する。
- 停止を確認するまで利用権は無効。生成を受け付けたbridgeからworker、各ComfyUI処理へ同じロックFDを継承する。復帰担当プロセスはそのFDの最後の保持者が終了するまで待つ。
- FDを閉じる際に明示的なLOCK_UNを発行しないため、起動元が先に終了しても残ったComfyUI処理のロックを解除しない。
- アプリ再起動時も、画像生成・LLM復帰処理の記録が残る間は新しいLLMを起動しない。復帰担当自体が強制終了した場合の記録は自動削除せず、調査が必要な状態として扱う。
- Krea2の生成画面・生成API・実行サービス・HTTPキュー監視を削除した。保存済みキャッシュの確認と明示削除は汎用ストアへ分離した。既存画像・キャッシュ・モデルの削除はしていない。
- bridgeの画像生成ライフサイクル版は2。新しいsupervisorは版1のbridgeを再利用しない。
- 英訳保存、停止、生成、復帰の状態を画面へ表示する。送信前の失敗は同じ画面で準備をやり直せる。送信結果が不明な場合は同じジョブの状態を照会し、自動再生成しない。
