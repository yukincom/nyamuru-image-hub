# ComfyUIワークフロー接続仕様

採用日: 2026-10-30

**状態: 登録・選択・API生成経路・5候補・採用後透過を正本へ実装。局所試験済み、実モデルによる受入は未実施。** 実装順序は[実装計画](2026-10-30-comfyui-workflow-plan.md)に定める。

ComfyUIで作成・確認したワークフローをニャムルに登録し、環境設定で選択して使用する。ニャムルは制作中の指示・参照画像を渡し、ComfyUIが生成した画像を候補として受け取る。ワークフローの編集場所はComfyUI、作品への採用場所はニャムルとする。

## 1. 接続と責務

```text
ComfyUIで編集 → API形式JSONを書き出す → ニャムルの環境設定で登録・選択
                                              ↓
ニャムルの生成画面 → ローカルbridge → ComfyUIの標準API → 生成結果
         ↑                                                   ↓
         └──────── 候補選択・必要な透過・新規レイヤーへの追加 ────┘
```

- ComfyUIは生成グラフ、モデル、カスタムノード、Python環境、推論を管理する。
- ニャムルは登録定義、入力の対応付け、生成ジョブ、候補選択、作品への追加を管理する。ComfyUIのインストール領域へニャムルのコードを埋め込まず、管理venvをコピー・上書きしない。
- 通信は既存のローカルbridgeから行う。LAN利用でも、ブラウザーが別PCのlocalhostへ直接接続する構成にはしない。接続先URLのlocalhostはbridgeが動くMacを指す。
- 接続先には既存の `comfyuiUrl` を使用する。空欄時のbridge既定値とloopback HTTPの制限を維持し、環境設定で選んだ接続先を実際の生成にも使用する。
- MCPは外部エージェントからComfyUIを操作する追加の入口にできるが、ニャムルの生成ボタンに必須の中継にはしない。標準ノードで不足する処理だけを、必要性の確認後に独立したカスタムノードとして扱う。

標準APIの画像アップロード、生成受付、履歴・進捗、画像取得を使う。[ComfyUI公式API仕様](https://docs.comfy.org/development/comfyui-server/comms_routes)が通信の基準となる。API接続によってニャムルのファイルをComfyUIの更新対象から分離するが、更新後のノード互換性まで保証するものではない。

## 2. 環境設定の選択窓口

既存の「環境設定 → モデル → ローカル画像生成」に次の項目をまとめる。通常の制作画面へノード編集UIを持ち込まない。

| 項目・操作 | 役割 |
|---|---|
| ComfyUI接続先／接続を確認 | 実際の生成先を指定し、起動中サーバーへの接続を確認する |
| ワークフロー一覧／使用するワークフロー | 登録した名前で選択する。選択したものを、この端末の通常生成に使う |
| ファイルから追加 | ComfyUIで書き出したAPI形式JSONをブラウザーのファイル選択で読み込み、名前を付けて登録する |
| ファイルから更新 | 選んだ登録を、再書き出ししたAPI形式JSONで更新する。登録IDを保ち、定義の版を進める |
| 入出力の設定 | 指示文、参照画像、シード、画像寸法などの受け渡し先と、完成画像の取得元を対応付ける |
| 利用可否を確認 | 接続先と、対応付けた入出力の存在を確認する。画像生成は開始しない |
| 登録解除 | ニャムルの登録だけを解除する。ComfyUIの元ファイル・モデル・既存の生成結果は削除しない |

選択・登録・更新だけでは推論、作品の変更、Undo、作品保存を発生させない。未選択や接続不可の場合は生成準備画面で理由と設定への入口を示し、別ワークフローへ自動で切り替えない。選択中の登録を解除した場合は未選択へ戻す。

端末の初期選択は `nyamuru_qwen_turbo_3images`、接続先は `http://127.0.0.1:8188`。この標準設定の人物生成はネーム・優先設定画・3Dの順で送り、ピンポイント修正・文字等は実際の画像枚数に合う通常Qwen定義を使う。利用者が別の定義を明示した場合はその登録を使う。生成画面には実行する定義名を表示する。

「接続できる」「定義と入力が対応している」「実生成を確認した」を区別する。読取だけの確認で生成成功・画質・速度を確認済みとは表示しない。欄の近くに必要な案内を表示し、ヘルプポップアップは追加しない。

## 3. 登録形式と保存

初期版で受け付けるのは、`class_type` と `inputs` を持つノードID別の**API実行形式JSON**。ComfyUIの編集画面用JSONをそのまま実行したり、未知のグラフを推測して変換したりしない。形式が違う場合はComfyUIでAPI形式を書き出すよう案内する。

登録定義は、ID、表示名、版、APIグラフ、入力の対応付け、出力の対応付け、受け付ける入力条件を持つ。入力条件には新規／画像参照、参照画像の枚数、出力寸法を指定できるか、プロンプトの扱いを含める。

- 定義本体はbridge側の `.local-generation/workflows/` に保存する。登録APIへJSONの内容を渡し、ブラウザーのファイルパスやComfyUI内部のディレクトリ配置に依存しない。
- 選択IDは既存の端末用 `generationPreferences.local`、URLは `localModelPreferences.comfyuiUrl` に保存する。Qwen接続済み専用キーとの二重管理を作らない。
- 同じbridgeを使う端末は登録一覧を共有し、どの登録を使うかは端末ごとに選ぶ。登録更新時は編集中の版を照合し、別端末の更新を無言で上書きしない。
- 作品のOMNY・作画ルールへ環境依存のURL・ローカルパスを混ぜない。ワークフロー選択は作品のUndo対象にしない。
- ComfyUIでの編集後は「API形式で書き出す → ファイルから更新 → 対応付けを確認」で反映する。自動監視や双方向のグラフ編集は初期版に含めない。
- 準備済みジョブには、その時点の定義・版・接続先・最終入力を固定して保存する。登録の更新・解除や既定の切り替えで、実行中ジョブと保存済み結果を書き換えない。

ブラウザー内の会話・音声操作は、その端末で選択したID・URLを同じprepareへ渡す。Hermes等のブラウザー外の入口は、登録一覧から選んだIDと接続先を要求へ明示する。ブラウザーのlocalStorageを読める前提にせず、別端末の最後の選択を推測して流用しない。接続先を省略した場合だけbridgeの明示された既定値を使い、実行前に解決済みの接続先を示す。ワークフローIDは省略不可とする。

## 4. 入出力の対応付け

| ニャムル側の値 | 渡し方・保持する条件 |
|---|---|
| 指示文 | 指定した文字列入力へ渡す。参照番号と役割の対応、利用者の修正、写植・描き文字の日本語本文を保持する |
| 参照画像 | 役割と順番を保持してアップロードし、返された画像名を指定した画像入力へ渡す。キャンバス、人物資料、修正指示画像を勝手に交換・合成しない |
| シード | 候補ごとに確定した数値を、登録されたシード入力へ渡す。ComfyUI編集画面の「実行後に増分」等へ依存しない |
| 幅・高さ | 対応する入力がある定義へ渡す。固定寸法の定義なら固定値を事前表示し、配置枠と同じ寸法だと扱わない |
| 完成画像 | 登録した出力ノードと画像位置から取得する。途中プレビューや別枝の画像を完成品と推測しない |

対応付けではノード名・入力名を一覧から選ぶ。ノードID等はこの詳細設定とエラーの特定に限って表示する。登録時はAPI形式と受け渡し先の存在・重複・参照枚数を確認し、利用可否確認では対応付けた入出力とAPIの `/object_info` を照合する。ノード内部の型、値の範囲、モデルなどの選択肢、リンク・循環、動的入力の詳細はComfyUIの実行受付に任せる。対応付けていない枝の設定を独自検査で拒否しない。

入力欄には複数の受け渡し先を設定できる。受け渡し先として登録されていない値・接続・モデル・サンプラー設定はグラフの値を保持する。プロンプトや画像の役割をノード名だけから推測して確定しない。

参照枚数の不足・超過は実行前に示す。不要な参照を捨てる、人物資料を一枚へ合成する、指定していない画像を空欄へ補う処理は行わない。可変枚数は定義に明示した対応範囲内で扱い、グラフの任意の枝を自動で作り替えない。

Qwen用の登録定義では既存の承認済みプロンプト組立・英訳・文字の定型経路を接続する。汎用の登録定義は、利用者が確認した指示文をそのまま渡すことを基本とし、Qwen固有の画像トークンや背景指示を無条件に付加しない。入力処理の種類を定義へ保存して、実行時にモデル名から推測しない。

## 5. 生成と候補選択

初期対応はローカルモデルによる静止PNGの生成。ComfyUIで単独実行を確認でき、上記の入出力を対応付けられるワークフローを対象とする。任意の動画・音声・3D出力や外部有料APIノードを包括的に対応済みとはしない。

1. 選択した登録を使い、指示文・参照画像・対応範囲を確認してジョブを準備する。
2. 既存の明示的な生成操作でAPIへ送信する。接続確認や設定保存から送信しない。
3. 1回のワークフロー実行から指定した完成画像を1枚取得する。5候補は同じ入力と異なる5シードで順次実行し、ニャムルの1ジョブにまとめる。内部バッチで複数画像を返す定義は、初期版では取得する1枚を明示できる場合だけ扱う。
4. 5候補をニャムルで比較する。採用が必要なところで会話・音声経路も選択待ちにする。
5. 人物の透過処理が設定されている場合は、選ばれた1枚だけをニャムル側のコードで処理する。
6. 結果を確認し、「新規レイヤーとして追加」で同じ対象フォルダーの最上段へ追加する。あたり・既存レイヤー・手動ロックを保持し、1回のUndoで追加を戻せる。

Hermesのプロンプトプレビューは保存済み定義と入力だけで行い、ComfyUIへの接続・モデル解放確認・ジョブ保存を要求しない。生成準備は共通serviceへ一度渡し、必要な接続確認をそこで行う。

5シードと取得対象を準備時に固定する。入力アップロードと英訳は同一ジョブ内で共用し、同じグラフ入力はComfyUIのキャッシュを利用できる形にする。モデルの読込回数やピークメモリをAPI利用だけで保証しない。

候補が途中まで完成してエラーになった場合は取得済み候補を残し、未完了を表示する。初期版では全候補完了を通常の採用画面へ進む条件とし、残りを無断で再送・再生成しない。作品へ自動挿入しない。

[人物生成の単色背景・クロマキー透過仕様](2026-10-30-chroma-key-generation-spec.md)は、対応するQwen人物定義の後処理として接続する。透過設定はジョブ単位であり、環境設定のワークフロー選択とは分ける。ページ・コマ・背景の生成には人物用の背景抜きを適用しない。

## 6. APIとジョブの所有

| 用途 | ComfyUI API |
|---|---|
| サーバーとノードの確認 | `GET /system_stats`、`GET /object_info` |
| 参照画像の配置 | `POST /upload/image` |
| 実行受付 | `POST /prompt` |
| 進捗と結果の照合 | `/ws`、`GET /queue`、`GET /history/{prompt_id}` |
| 画像取得 | `GET /view` |
| 取消し | `POST /api/jobs/{prompt_id}/cancel`。対象指定に対応しないサーバーでは制限を表示し、全体停止へ代替しない |

APIグラフには対象定義と入力だけを反映し、外部ファイルを実行コードとして読み込まない。登録時・利用可否確認時に `/prompt` を試し打ちしない。

既存の生成ジョブ保存・候補選択・履歴を再利用し、ニャムルのジョブIDと各候補のComfyUI `prompt_id` を対応付ける。受付しただけで完了扱いにせず、指定出力を取得してから候補を完成扱いにする。

送信のタイムアウト・切断は結果不明として照合し、同じ候補を自動で再送しない。送信前に照合用IDを保存し、返答を失った場合にキュー・履歴から確認できる形を採る。履歴消去等で照合できなければ未確定を表示し、成功にも失敗にも読み替えない。

取消しはそのニャムルジョブに属する待機・実行だけを対象にする。対象指定の停止が使えない場合はその制限を表示し、全キュー削除や全体停止で代用しない。設定変更・画面を閉じる操作から、ユーザーが別途送ったComfyUIジョブを止めない。

## 7. 起動とメモリ

ComfyUIの起動・終了・更新はDesktop側に任せる。ニャムルは起動済みサーバーへ接続し、未起動なら起動を案内する。生成の終了条件をComfyUIプロセスの終了待ちにしない。

文章LLMの一時停止・復帰は既存の利用セッションを通す。ニャムルが休止したLLMだけを復帰し、ComfyUIのユーザー所有プロセスを終了させない。画像モデル解放が必要な構成では他の待機・実行ジョブがないことを確認して解放し、解放待ちとLLM復帰待ちを区別して表示する。

送信後にbridgeやworkerが終了しても、外部ComfyUIのジョブは継続し得る。子プロセスの終了やファイル記述子の閉鎖だけをLLM復帰の根拠にしない。復帰担当は保存済みジョブとComfyUIの状態を照合し、実行中・結果不明の間は復帰待ちを維持する。接続を回復できない場合は、その状態を明示して利用者の対処を待つ。

標準の `/free` は要求受付のみを返すため、解放完了は同梱の [nyamuru_memory_release拡張](../comfyui_extensions/nyamuru_memory_release/README.md) で観測する。利用者承認に基づいて作成した独立拡張で、ComfyUI本体とvenvは変更しない。拡張が未配置の状態では生成前に不足を示す。拡張の作成・模擬試験と、実ComfyUIへの配置・再起動・メモリ回収の確認を区別する。

CPUでのVAE実行、参照キャッシュ、attention、MPSメモリ上限は、採用するQwenワークフローとDesktop実行環境で確認する。API化によって別プロセスの工程終了と同じメモリ解放が起きるとは扱わない。必要な調整は標準ノード・正式な起動設定を優先し、本体への直接パッチを前提にしない。

## 8. 更新と対象外

ComfyUI更新後は、登録定義の対応付けた入出力を確認できるようにする。実行受付でComfyUIが検出した型・モデル等の不一致はその応答を表示し、保存したグラフやモデル名を自動で書き換えない。必要な修正はComfyUIで行い、ファイルから更新する。

実モデル生成、通常サーバーの再起動、モデル取得、venvの移設・削除は今回の局所実装・検証には含めていない。VLM・OCR・音声分類のPython接続は別の責務とし、画像生成のAPI化を理由に変更しない。
